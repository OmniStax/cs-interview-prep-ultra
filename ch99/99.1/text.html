The problem

A sorted array of numbers and a target. Is there a pair of numbers in the array that adds up to the target, and if so, where?

Take 2, 4, 5, 7, 9, 12, 14, 18 and the target 21.

1. The obvious way

Add up every pair and look. Eight numbers make 28 pairs, and the table below has one cell for each: row $\htmlData{ref=pair-l}{i}$, column $\htmlData{ref=pair-r}{j}$. A cell shows its sum only once the code has added it up.

This works on any array, sorted or not, and never uses the fact that this one is sorted. For $n$ numbers it adds up as many as $n(n-1)/2$ pairs.

2. What the obvious way wastes

Now use the order. The first pair to try is the smallest number with the largest. Its sum is one number, but because the array is sorted it says something about other pairs too. You decide which.

3. The fast way

What you just did by hand is the whole algorithm. $\htmlData{ref=pair-l}{i}$ starts at the first number and $\htmlData{ref=pair-r}{j}$ at the last; each sum either is the target or throws out a row or a column, and the pointer that moves is the one whose number is finished.

What stays true from start to finish: any pair that adds up to the target lies between $\htmlData{ref=pair-l}{i}$ and $\htmlData{ref=pair-r}{j}$. Each step moves one pointer inward, so at most $n - 1$ sums are added up.

The source’s words

First suppose the answer is 1 and n. If we find that $num[1]+num[n]\gt \mathit{target}$, we need to make one of the elements smaller, and $\mathit{num}[1]$ cannot get any smaller, so we decrease the pointer at $n$ by one, making the larger number smaller.

Likewise, if we find that $num[1]+num[n]\lt \mathit{target}$, we need to make one of the elements larger, but $\mathit{num}[n]$ cannot get any larger, so we increase the pointer at 1 by one, making the smaller number larger.

4. The insight

Insight

On sorted data, one comparison settles many candidates at once. Here: a sum that is too small rules out every pair with the smaller number, and a sum that is too big rules out every pair with the larger one.

Where the same insight does the work:

  • 3SUM (Section 2.3): fix one number, then this, once per number.
  • Merging two sorted arrays (Section 2.3): the smaller of the two heads is smaller than everything left in both.
  • Binary search (not built yet): one comparison with the middle rules out half the array.

One more insight on top of this one:

  • Variable-size sliding windows (Section 2.3): both pointers move the same way, and what is ruled out is every window that starts further left.
