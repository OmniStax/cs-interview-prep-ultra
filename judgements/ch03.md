  the source name and URL out of view, as A and B, and judged A-then-B and B-then-A. Each
  verdict is *clearly better*, *slightly better* or *even*. Sources are named below only
  in the write-up, after the verdict. Where more than two candidates were serious, the
  top one was compared with each of the others; the rest are ranked by those comparisons.
- **Pass 1** on lucidity alone. **Pass 2** revisited only close calls and moved each
  toward its neighbours' majority source (chapter 3 neighbours plus the chapter 1
  concept `interface-vs-implementation`, whose only treatment is ODS). Pass 2 was run
  twice; the second run changed nothing.
- **Checks.** Every check is my own code, written from what the passage says, run
  against brute force. Script: `/tmp/claude-0/-home-user/249e18c8-3562-5258-9ce2-fd057404a6b0/scratchpad/checks/ch03_checks.py`
  (34 checks), plus `/tmp/claude-0/-home-user/249e18c8-3562-5258-9ce2-fd057404a6b0/scratchpad/checks/ex_checks.py`
  for exercise data. **I could not run any cached source code.** The permission system
  refused it ("Code from External"). So no reference solution in the cache has been run
  against its tests, and no passage's own code has been run. What I did instead: I read
  each reference, re-implemented the algorithm the prose gives and tested that, and ran my

  samples). Every exercise below is **provisional** until the orchestrator, or someone

- **User ruling applied (received mid-run):** the doocs "> **Thinking**" blockquotes

**Pairwise, Wikipedia (A) and the ODS LIFO paragraph (B):** A is clearly better in both
orders.
- *Terms defined before use.* A defines push, pop and peek before using them ("Pop, which
  removes the most recently added element"). B defines the stack through the Queue
  interface: "A very common queueing discipline is the LIFO (last-in-first-out)
  discipline … the names of add(x) and remove() are changed to push(x) and pop()". In
  this book the stack comes first (the concept map dropped the queue edge for exactly
  this reason), so add(x), remove() and "queueing discipline" would not be defined yet.
- *Coverage of the row (push, pop, peek, O(1) on array or list).* A covers all of it,
  including underflow ("If the stack is empty, an underflow condition will occur upon
  execution of either the "peek" or "pop" operation") and the dynamic array ("requires
  amortized O(1) time"). B has no peek, no cost and no implementation.

**Against the others:**
- Wikipedia is clearly better than Wikibooks #Stacks, which contains wrong or muddled
  claims: "displaying the contents of the stack (peek or top)"; "get-size() runs in at
  worst O(N)"; and an unexplained jump, "Since all operations are at the top of the stack,
  the array implementation is now much, much better", followed by a pointer to a
  StackVector that is not there.
- OpenDSA's prose leaves its answers to slideshows that are not cached: "The only
  important design decision to be made is which end of the array should represent the top
  of the stack" is answered only inside `astackTopCON`.
- Aspnes is lucid and correct. It ranks behind Wikipedia because it is C with pointers,
  and its figures ("For example here's what happens the linked list above looks like…")
  are missing from the cache.

**Checks:**
- I traced Wikipedia's array pseudocode by hand. top starts at 0; push writes
  `items[top]` and then increments; pop decrements and then reads. It is correct, and
  empty means top = 0.
- The linked-list push and pop both work at the head. Correct.
- The amortized O(1) claim for the dynamic array is the chapter 2 result.

**Builder notes:**
- The notation clashes with the ODS neighbours: Wikipedia uses `procedure push(stk: stack,
  x: item)` pseudocode, and ODS uses `push(x)` methods. This is not decisive here because
  the margin is clear.
- The GIFs are CC BY-SA 4.0, as listed in the dossier.
- For runnable code: `thealgorithms-python:data_structures/stacks/stack.py` (MIT) for

### dual-array-deque: ODS (only candidate)

**Checks:**
- The lemma's arithmetic holds: Φ1 > n/2 and Φ0 ≤ 1, so at least n/2 − 1 operations
  separate two rebalances.
- The "i < n/4 means the front case" step follows from the balance invariant
  3·front.size() ≥ back.size().
- **Erratum found.** The prose says "If i<front.size(), then add(i,x) gets implemented by
