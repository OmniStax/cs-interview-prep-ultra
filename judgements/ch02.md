## How this run was done

  source names and URLs out of view, as A and B, and judged A-then-B and B-then-A. Each
  verdict is *clearly better*, *slightly better* or *even*. Sources are named below only
  in the write-up, after the verdict. With more than two serious candidates, the top one
  was compared with each of the others, and the rest are ranked by those comparisons.
- **Pass 1** used lucidity alone. **Pass 2** revisited the close calls and moved each one
  toward its neighbours' majority source. The neighbours are the concept-map
  prerequisites and dependants, the adjacent sections, and the chapter 3 winners already
  on file in `judgements/ch03.md`. Pass 2 ran twice, and the second run changed nothing.
- **User ruling applied (received mid-run):** `eh-dsa` and `algowiki` are not
  candidates at all. doocs "> **Thinking**" blocks are excluded: a doocs write-up is
  judged on its other prose only, and the ones whose only prose is a Thinking block
  (0202, 0203, 0438, 0707, 0930) are not candidates. No provenance escalation is needed.
  None of the winners below was close to an excluded candidate after the ruling.
- **Decision 15 applied to doocs:** a doocs write-up is eligible only when an open

  2536 as explanations (the dossier's "no open exercise" list). No doocs write-up won.
- **Errata are notes, not edits.** As in chapter 3, a factual slip inside a winning
  passage is listed for the builder as an erratum note to attach. The source text is not
  silently changed. Where a rival had no error, the error counted against the passage.
- **Checks.** These checks used my own code, run against brute force, plus the sources'

## 2.1 Arrays and the list interface

### array: Wikipedia

**Ranked:**
1. Wikipedia Array (locator above)
2. Aspnes 223 §4.9.5.1 + §4.9.5.3
3. Wikibooks Data_Structures/Arrays
4. lt-morelli 9.1
5. OI Wiki lang/array
6. lt-busbee 6.01/6.02/6.09
7. dsa-dummies Array.py
8. itsy-bitsy List
9. Holden Pointers#Arrays

**Pairwise, Wikipedia (A) and Aspnes (B):** A is slightly better in both orders. This
was the hardest call in the chapter.
- *Defined before use.* A stands alone and is language-neutral: "an array is a data
  structure consisting of a collection of elements … each identified by at least one
  array index". B opens on pointers the book has not taught: "The array name acts like a
  constant pointer to the zeroth element of the array". It also leans on §4.9.5's
  pointer-arithmetic rules, which in this book come *after* `array`, because the map's
  edge runs array → pointer-arithmetic.
- *Example next to the abstraction.* Both have one. A: "ten 32-bit (4-byte) integer
  variables … at memory addresses 2000, 2004, 2008, ..., 2036 … the element with index i
  has the address 2000 + (i × 4)". B: the `int a[3][6]` layout picture with "24+16 bytes
  from a, the position of 10".
- *Why.* A: "Arrays are useful mostly because the element indices can be computed at run
  time." B gives none.
- *Correctness.* Each has one wrong sentence.
  - A, in ===One-dimensional arrays===: "the base address B is replaced by B + 30c, then
    the indices of those same elements will be 31 to 35". With address = B + c·i, the
    replacement must be B − 30c; with B + 30c the indices become −29 to −25.
  - B: "200 bytes for a above and 400 for cp". That assumes 4-byte pointers, while the
    same notes say "On a typical 64-bit machine, each will be allocated 8 bytes" (so it
    would be 800).

  Both are attached as errata. A's slip sits in a side remark about re-basing. B's
  contradicts its own stated machine. Neither decided the pair.
- *Coverage of the row (contiguous, O(1) by address arithmetic, multi-dimensional,
  jagged).* A covers all of it: "Both store and select take (deterministic worst case)
  constant time", k-dimensional addressing, and Iliffe vectors that "allow jagged arrays,
  where each row may have a different size". B covers contiguity, multi-dimensional
  arrays and pointer-to-row arrays, but never states the cost.

**Pass 2:** A's neighbours `pointer-arithmetic` and `pointer-to-pointer` both went to
Wikipedia *Pointer*, which keeps the call. The other equilibrium (Aspnes for both
`array` and `pointer-arithmetic`) is consistent too. Aspnes 4.9.5 and 4.9.5.1 are one
run of text, so it is listed for the reconciliation pass.

**Against the others:**
- Wikibooks clashes with itself: "Think of a notebook with pages numbered 1 through 12",
  then an ADT "indexed from 0 to n-1". It is also wrong about C: "require the type and
  length information of an array to be known at run time (such as C)". C needs them at
  compile time.
- OI Wiki lang/array is C++ declaration syntax, with no address arithmetic or cost.
- dsa-dummies is wrong: "array.sort() - Time complexity: O(n log n) …, Space complexity:
  O(1)". Timsort uses O(n) extra space. It also gives append as O(1) without
  "amortized".
- itsy-bitsy's cost table is unusable in a book: "Polynomial O(N ^ 2) SHITTY".
- Holden is wrong: "a[i] = * (a + i * sizeof(type)" (see the checks).

**Checks:**
- Address example: 2000 + 4·9 = 2036; 0x7D0 = 2000 and 0x7F4 = 2036. Correct.
- 1D re-basing, worked by hand: address of element i = B + c·i = (B − 30c) + c·(i + 30),
  so B − 30c gives indices 31 to 35. A's B + 30c is wrong.
- 2D re-basing: replacing B with B + c₁ − 3c₂ maps rows 1..10 to 0..9 and columns 1..20
  to 4..23. Correct.
- `c/wp_ptr.c`:
  - Aspnes `a[1][4]` sits 40 bytes from `a` and holds 10. Correct.
  - Holden's formula: `*(h + 1*sizeof(int))` returns `h[4]` (14), not `h[1]` (11). Wrong.

**Builder notes:**
- Erratum for ===One-dimensional arrays===: "B + 30c" should read "B − 30c".
- ===Multidimensional arrays=== labels a C array as "a<sub>11</sub>, a<sub>12</sub> …":
  1-based labels on a 0-based array. Flag it in the erratum note too.
- Figures: 1D/2D/3D array diagram.svg (CC BY 4.0), Array of array storage.svg (PD).
- Python/JS code: none needed. The passage's examples are formulas and C declarations.

### dynamic-array-cost: ODS

**Ranked:**
1. ODS lemma + Summary
2. Wikipedia #Performance + Amortized_analysis#Dynamic array
3. Wikibooks Amortized Analysis box
4. OpenDSA (fixed-size list costs only)

**Pairwise:** ODS is slightly better in both orders.
- It proves its claim: "the total time spent during all calls to resize() is O(m)". The
  proof is by counting the operations between resizes.
- Wikipedia states the costs ("Inserting or deleting an element at the end of the array
  (constant amortized time)") without proof.

Continuity agrees.

**Checks (`dyn.py`, `run_ods_tests.py`):**
- ODS policy (grow to 2n when full, shrink to 2n when a.length ≥ 3n) under 200,000 mixed
  operations. Copies per operation: 1.311 for append only, 0.037 for random, 0.010 for
  thrashing at a boundary, and 0.997 for grow/shrink waves. Always O(1) amortized. A
  naive shrink-at-half policy thrashes at 929 copies per operation, which is why the
  3n threshold matters.
- Wikipedia's growth-factor claims hold. a = 1.5 gives 3.10 cost per insert
  (a/(a−1) = 3) and maximum waste 0.5n = (a−1)n. a = 2 gives 2.05 and 1.0n.
- Wikipedia's "threshold must be strictly smaller than 1/a" is consistent with the
  thrash result.
- Wikipedia's "insertEnd" starting from capacity 0 stays at capacity 0 and writes out of
  bounds.
- Wikipedia's CPython growth sequence (0, 4, 8, 16, 24, 32, 40, 52, 64, 76) matches
  CPython 3.13.
- ODS ArrayStack and FastArrayStack pass ODS `listtest.py`, run with two runtime shims:
  `numpy.object` aliased to `object`, and a Python 3 `__eq__` in place of the Python 2
  `it.next()`. This confirms chapter 3's note that the ODS Python needs a port before
  the runners use it.

**Builder notes:**
- ODS erratum: the proof says "All that remains is to show that the number of calls …
  is at least n_i/2", but the bound it uses and proves is n_i/2 − 1.
- ODS shrinks at a.length ≥ 3n. The concept row's CIU wording is "halve when size falls
  to a quarter", and the CIU vector exercise (below) asks for the quarter rule. The
  card should say that both thresholds work and why (hysteresis).
