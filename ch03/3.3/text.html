The Deque interface

A Deque is a generalization of both the FIFO Queue and LIFO Queue (Stack). A Deque represents a sequence of elements, with a front and a back. Elements can be added at the front of the sequence or the back of the sequence. The names of the Deque operations are self-explanatory: $\mathrm{add\_first}(x)$, $\mathrm{remove\_first}()$, $\mathrm{add\_last}(x)$, and $\mathrm{remove\_last}()$. It is worth noting that a Stack can be implemented using only $\mathrm{add\_first}(x)$ and $\mathrm{remove\_first}()$ while a FIFO Queue can be implemented using $\mathrm{add\_last}(x)$ and $\mathrm{remove\_first}()$.

ArrayDeque: Fast Deque Operations Using an Array

The ArrayQueue from the previous section is a data structure for representing a sequence that allows us to efficiently add to one end of the sequence and remove from the other end. The ArrayDeque data structure allows for efficient addition and removal at both ends. This structure implements the List interface by using the same circular array technique used to represent an ArrayQueue.

The implementation of $\mathrm{add}(\htmlData{ref=i}{i},x)$ is a little more interesting. As usual, we first check if $\htmlData{ref=a}{a}$ is full and, if necessary, call $\mathrm{resize}()$ to resize $\htmlData{ref=a}{a}$. Remember that we want this operation to be fast when $\htmlData{ref=i}{i}$ is small (close to 0) or when $\htmlData{ref=i}{i}$ is large (close to $\htmlData{ref=n}{n}$). Therefore, we check if $\htmlData{ref=i}{i}<\htmlData{ref=n}{n}/2$. If so, we shift the elements $\htmlData{ref=a}{a}[0],\ldots,\htmlData{ref=a}{a}[\htmlData{ref=i}{i}-1]$ left by one position. Otherwise ($\htmlData{ref=i}{i}\ge \htmlData{ref=n}{n}/2$), we shift the elements $\htmlData{ref=a}{a}[\htmlData{ref=i}{i}],\ldots,\htmlData{ref=a}{a}[\htmlData{ref=n}{n}-1]$ right by one position. See Figure 2.3 for an illustration of $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(x)$ operations on an ArrayDeque.

By doing the shifting in this way, we guarantee that $\mathrm{add}(\htmlData{ref=i}{i},x)$ never has to shift more than $\min\{ \htmlData{ref=i}{i}, \htmlData{ref=n}{n}-\htmlData{ref=i}{i} \}$ elements. Thus, the running time of the $\mathrm{add}(\htmlData{ref=i}{i},x)$ operation (ignoring the cost of a $\mathrm{resize}()$ operation) is $O(1+\min\{\htmlData{ref=i}{i},\htmlData{ref=n}{n}-\htmlData{ref=i}{i}\})$.

The implementation of the $\mathrm{remove}(\htmlData{ref=i}{i})$ operation is similar. It either shifts elements $\htmlData{ref=a}{a}[0],\ldots,\htmlData{ref=a}{a}[\htmlData{ref=i}{i}-1]$ right by one position or shifts the elements $\htmlData{ref=a}{a}[\htmlData{ref=i}{i}+1],\ldots,\htmlData{ref=a}{a}[\htmlData{ref=n}{n}-1]$ left by one position depending on whether $\htmlData{ref=i}{i}<\htmlData{ref=n}{n}/2$. Again, this means that $\mathrm{remove}(\htmlData{ref=i}{i})$ never spends more than $O(1+\min\{\htmlData{ref=i}{i},\htmlData{ref=n}{n}-\htmlData{ref=i}{i}\})$ time to shift elements.

def remove(self, i):
    x = self.a[(self.j+i)%len(self.a)]
    if i < self.n / 2:

Summary

The following theorem summarizes the performance of the ArrayDeque data structure:

Theorem

An ArrayDeque implements the List interface. Ignoring the cost of calls to $\mathrm{resize}()$, an ArrayDeque supports the operations

  • $\mathrm{get}(\htmlData{ref=i}{i})$ and $\mathrm{set}(\htmlData{ref=i}{i},x)$ in $O(1)$ time per operation; and
  • $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$ in $O(1+\min\{\htmlData{ref=i}{i},\htmlData{ref=n}{n}-\htmlData{ref=i}{i}\})$ time per operation.

Furthermore, beginning with an empty ArrayDeque, performing any sequence of $m$ $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$ operations results in a total of $O(m)$ time spent during all calls to $\mathrm{resize}()$.

DualArrayDeque: Building a Deque from Two Stacks

Next, we present a data structure, the DualArrayDeque that achieves the same performance bounds as an ArrayDeque by using two ArrayStacks. Although the asymptotic performance of the DualArrayDeque is no better than that of the ArrayDeque, it is still worth studying, since it offers a good example of how to make a sophisticated data structure by combining two simpler data structures.

A DualArrayDeque represents a list using two ArrayStacks. Recall that an ArrayStack is fast when the operations on it modify elements near the end. A DualArrayDeque places two ArrayStacks, called $\htmlData{ref=front}{\mathit{front}}$ and $\htmlData{ref=back}{\mathit{back}}$, back-to-back so that operations are fast at either end.

The $\mathrm{add}(\htmlData{ref=i}{i},x)$ method performs rebalancing of the two ArrayStacks $\htmlData{ref=front}{\mathit{front}}$ and $\htmlData{ref=back}{\mathit{back}}$, by calling the $\mathrm{balance}()$ method. The implementation of $\mathrm{balance}()$ is described below, but for now it is sufficient to know that $\mathrm{balance}()$ ensures that, unless $\mathrm{size}()<2$, $\mathrm{front.size}()$ and $\mathrm{back.size}()$ do not differ by more than a factor of 3. In particular, $3\cdot\mathrm{front.size}() \ge \mathrm{back.size}()$ and $3\cdot\mathrm{back.size}() \ge \mathrm{front.size}()$.

Next we analyze the cost of $\mathrm{add}(\htmlData{ref=i}{i},x)$, ignoring the cost of calls to $\mathrm{balance}()$. If $\htmlData{ref=i}{i}<\mathrm{front.size}()$, then $\mathrm{add}(\htmlData{ref=i}{i},x)$ gets implemented by the call to $\mathrm{front.add}(\mathrm{front.size}()-\htmlData{ref=i}{i}-1,x)$. Since $\htmlData{ref=front}{\mathit{front}}$ is an ArrayStack, the cost of this is

$$O(\mathrm{front.size}()-(\mathrm{front.size}()-i-1)+1) = O(i+1) \enspace .\tag{2.1}$$

On the other hand, if $\htmlData{ref=i}{i}\ge\mathrm{front.size}()$, then $\mathrm{add}(\htmlData{ref=i}{i},x)$ gets implemented as $\mathrm{back.add}(\htmlData{ref=i}{i}-\mathrm{front.size}(),x)$. The cost of this is

$$O(\mathrm{back.size}()-(i-\mathrm{front.size}())+1) = O(n-i+1) \enspace .\tag{2.2}$$

Notice that the first case (2.1) occurs when $\htmlData{ref=i}{i}<\htmlData{ref=n}{n}/4$. The second case (2.2) occurs when $\htmlData{ref=i}{i}\ge 3\htmlData{ref=n}{n}/4$. When $\htmlData{ref=n}{n}/4\le \htmlData{ref=i}{i}<3\htmlData{ref=n}{n}/4$, we cannot be sure whether the operation affects $\htmlData{ref=front}{\mathit{front}}$ or $\htmlData{ref=back}{\mathit{back}}$, but in either case, the operation takes $O(\htmlData{ref=n}{n})=O(\htmlData{ref=i}{i})=O(\htmlData{ref=n}{n}-\htmlData{ref=i}{i})$ time, since $\htmlData{ref=i}{i}\ge \htmlData{ref=n}{n}/4$ and $\htmlData{ref=n}{n}-\htmlData{ref=i}{i}> \htmlData{ref=n}{n}/4$. Summarizing the situation, we have

$$\text{Running time of } \mathrm{add}(i,x) \le \begin{cases} O(1+ i) & \text{if $i< n/4$} \\ O(n) & \text{if $n/4 \le i < 3n/4$} \\ O(1+n-i) & \text{if $i \ge 3n/4$} \end{cases}$$

Thus, the running time of $\mathrm{add}(\htmlData{ref=i}{i},x)$, if we ignore the cost of the call to $\mathrm{balance}()$, is $O(1+\min\{\htmlData{ref=i}{i}, \htmlData{ref=n}{n}-\htmlData{ref=i}{i}\})$.

Balancing

Finally, we turn to the $\mathrm{balance}()$ operation performed by $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$. This operation ensures that neither $\htmlData{ref=front}{\mathit{front}}$ nor $\htmlData{ref=back}{\mathit{back}}$ becomes too big (or too small). It ensures that, unless there are fewer than two elements, each of $\htmlData{ref=front}{\mathit{front}}$ and $\htmlData{ref=back}{\mathit{back}}$ contain at least $\htmlData{ref=n}{n}/4$ elements. If this is not the case, then it moves elements between them so that $\htmlData{ref=front}{\mathit{front}}$ and $\htmlData{ref=back}{\mathit{back}}$ contain exactly $\lfloor \htmlData{ref=n}{n}/2\rfloor$ elements and $\lceil \htmlData{ref=n}{n}/2\rceil$ elements, respectively.

def _balance(self):
    n = self.size()
    mid = n//2
    if 3*self.front.size() < self.back.size() or 3*self.back.size() < self.front.size():
        f = ArrayStack()
        for i in range(mid):
            f.add(i, self.get(mid-i-1))
        b = ArrayStack()
        for i in range(n-mid):
            b.add(i, self.get(mid+i))
        self.front = f
        self.back = b

Here there is little to analyze. If the $\mathrm{balance}()$ operation does rebalancing, then it moves $O(\htmlData{ref=n}{n})$ elements and this takes $O(\htmlData{ref=n}{n})$ time. This is bad, since $\mathrm{balance}()$ is called with each call to $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$. However, the following lemma shows that, on average, $\mathrm{balance}()$ only spends a constant amount of time per operation.

Lemma

If an empty DualArrayDeque is created and any sequence of $m\ge 1$ calls to $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$ are performed, then the total time spent during all calls to $\mathrm{balance}()$ is $O(m)$.

Proof. We will show that, if $\mathrm{balance}()$ is forced to shift elements, then the number of $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$ operations since the last time any elements were shifted by $\mathrm{balance}()$ is at least $\htmlData{ref=n}{n}/2-1$. As in the proof of Lemma 2.1, this is sufficient to prove that the total time spent by $\mathrm{balance}()$ is $O(m)$.

We will perform our analysis using a technique knows as the potential method. Define the potential, $\Phi$, of the DualArrayDeque as the difference in size between $\htmlData{ref=front}{\mathit{front}}$ and $\htmlData{ref=back}{\mathit{back}}$:

$$\Phi = |\mathrm{front.size}() - \mathrm{back.size}()| \enspace .$$

The interesting thing about this potential is that a call to $\mathrm{add}(\htmlData{ref=i}{i},x)$ or $\mathrm{remove}(\htmlData{ref=i}{i})$ that does not do any balancing can increase the potential by at most 1.

Observe that, immediately after a call to $\mathrm{balance}()$ that shifts elements, the potential, $\Phi_0$, is at most 1, since

$$\Phi_0 = \left|\lfloor n/2\rfloor-\lceil n/2\rceil\right|\le 1 \enspace .$$

Summary

The following theorem summarizes the properties of a DualArrayDeque:

Theorem

A DualArrayDeque implements the List interface. Ignoring the cost of calls to $\mathrm{resize}()$ and $\mathrm{balance}()$, a DualArrayDeque supports the operations

  • $\mathrm{get}(\htmlData{ref=i}{i})$ and $\mathrm{set}(\htmlData{ref=i}{i},x)$ in $O(1)$ time per operation; and
  • $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$ in $O(1+\min\{\htmlData{ref=i}{i},\htmlData{ref=n}{n}-\htmlData{ref=i}{i}\})$ time per operation.

Furthermore, beginning with an empty DualArrayDeque, any sequence of $m$ $\mathrm{add}(\htmlData{ref=i}{i},x)$ and $\mathrm{remove}(\htmlData{ref=i}{i})$ operations results in a total of $O(m)$ time spent during all calls to $\mathrm{resize}()$ and $\mathrm{balance}()$.
