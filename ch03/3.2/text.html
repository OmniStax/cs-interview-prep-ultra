The Queue Interface

The Queue interface represents a collection of elements to which we can add elements and remove the next element. More precisely, the operations supported by the Queue interface are

  • $\mathrm{add}(x)$: add the value $x$ to the Queue
  • $\mathrm{remove}()$: remove the next (previously added) value, $y$, from the Queue and return $y$

Notice that the $\mathrm{remove}()$ operation takes no argument. The Queue’s queueing discipline decides which element should be removed. There are many possible queueing disciplines, the most common of which include FIFO, priority, and LIFO.

A FIFO (first-in-first-out) Queue, which is illustrated in Figure 1.1, removes items in the same order they were added, much in the same way a queue (or line-up) works when checking out at a cash register in a grocery store. This is the most common kind of Queue so the qualifier FIFO is often omitted. In other texts, the $\mathrm{add}(x)$ and $\mathrm{remove}()$ operations on a FIFO Queue are often called $\mathrm{enqueue}(x)$ and $\mathrm{dequeue}()$, respectively.

ArrayQueue: An Array-Based Queue

In this section, we present the ArrayQueue data structure, which implements a FIFO (first-in-first-out) queue; elements are removed (using the $\mathrm{remove}()$ operation) from the queue in the same order they are added (using the $\mathrm{add}(x)$ operation).

Notice that an ArrayStack is a poor choice for an implementation of a FIFO queue. It is not a good choice because we must choose one end of the list upon which to add elements and then remove elements from the other end. One of the two operations must work on the head of the list, which involves calling $\mathrm{add}(i,x)$ or $\mathrm{remove}(i)$ with a value of $i=0$. This gives a running time proportional to $n$.

To obtain an efficient array-based implementation of a queue, we first notice that the problem would be easy if we had an infinite array $\htmlData{ref=a}{a}$. We could maintain one index $\htmlData{ref=j}{j}$ that keeps track of the next element to remove and an integer $\htmlData{ref=n}{n}$ that counts the number of elements in the queue. The queue elements would always be stored in

$$\htmlData{ref=a}{a}[\htmlData{ref=j}{j}],\htmlData{ref=a}{a}[\htmlData{ref=j}{j}+1],\ldots,\htmlData{ref=a}{a}[\htmlData{ref=j}{j}+\htmlData{ref=n}{n}-1] \enspace .$$

Initially, both $\htmlData{ref=j}{j}$ and $\htmlData{ref=n}{n}$ would be set to 0. To add an element, we would place it in $\htmlData{ref=a}{a}[\htmlData{ref=j}{j}+\htmlData{ref=n}{n}]$ and increment $\htmlData{ref=n}{n}$. To remove an element, we would remove it from $\htmlData{ref=a}{a}[\htmlData{ref=j}{j}]$, increment $\htmlData{ref=j}{j}$, and decrement $\htmlData{ref=n}{n}$.

Of course, the problem with this solution is that it requires an infinite array. An ArrayQueue simulates this by using a finite array $\htmlData{ref=a}{a}$ and modular arithmetic. This is the kind of arithmetic used when we are talking about the time of day. For example 10:00 plus five hours gives 3:00. Formally, we say that

$$10 + 5 = 15 \equiv 3 \pmod{12} \enspace .$$

We read the latter part of this equation as “15 is congruent to 3 modulo 12.” We can also treat $\bmod$ as a binary operator, so that

$$15 \bmod 12 = 3 \enspace .$$

More generally, for an integer $a$ and positive integer $m$, $a \bmod m$ is the unique integer $r\in\{0,\ldots,m-1\}$ such that $a = r + km$ for some integer $k$. Less formally, the value $r$ is the remainder we get when we divide $a$ by $m$. In many programming languages, including C, C++, and Java, the mod operate is represented using the % symbol.

Modular arithmetic is useful for simulating an infinite array, since $i\bmod \mathrm{length}(\htmlData{ref=a}{a})$ always gives a value in the range $0,\ldots,\mathrm{length}(\htmlData{ref=a}{a})-1$. Using modular arithmetic we can store the queue elements at array locations

$$\htmlData{ref=a}{a}[\htmlData{ref=j}{j}\bmod \mathrm{length}(\htmlData{ref=a}{a})],\htmlData{ref=a}{a}[(\htmlData{ref=j}{j}+1)\bmod \mathrm{length}(\htmlData{ref=a}{a})],\ldots,\htmlData{ref=a}{a}[(\htmlData{ref=j}{j}+\htmlData{ref=n}{n}-1)\bmod \mathrm{length}(\htmlData{ref=a}{a})] \enspace.$$

This treats the array $\htmlData{ref=a}{a}$ like a circular array in which array indices larger than $\mathrm{length}(\htmlData{ref=a}{a})-1$ “wrap around” to the beginning of the array.

The only remaining thing to worry about is taking care that the number of elements in the ArrayQueue does not exceed the size of $\htmlData{ref=a}{a}$.

To implement $\mathrm{remove}()$, we first store $\htmlData{ref=a}{a}[\htmlData{ref=j}{j}]$ so that we can return it later. Next, we decrement $\htmlData{ref=n}{n}$ and increment $\htmlData{ref=j}{j}$ (modulo $\mathrm{length}(\htmlData{ref=a}{a})$) by setting $\htmlData{ref=j}{j}=(\htmlData{ref=j}{j}+1)\bmod \mathrm{length}(\htmlData{ref=a}{a})$. Finally, we return the stored value of $\htmlData{ref=a}{a}[\htmlData{ref=j}{j}]$. If necessary, we may call $\mathrm{resize}()$ to decrease the size of $\htmlData{ref=a}{a}$.

def remove(self):
    x = self.a[self.j]
    self.j = (self.j + 1) % len(self.a)
    self.n -= 1
    if len(self.a) >= 3*self.n: self._resize()
    return x

Finally, the $\mathrm{resize}()$ operation is very similar to the $\mathrm{resize}()$ operation of ArrayStack. It allocates a new array, $\htmlData{ref=b}{b}$, of size $2\htmlData{ref=n}{n}$ and copies

$$\htmlData{ref=a}{a}[\htmlData{ref=j}{j}],\htmlData{ref=a}{a}[(\htmlData{ref=j}{j}+1)\bmod \mathrm{length}(\htmlData{ref=a}{a})],\ldots,\htmlData{ref=a}{a}[(\htmlData{ref=j}{j}+\htmlData{ref=n}{n}-1)\bmod \mathrm{length}(\htmlData{ref=a}{a})]$$

onto

$$\htmlData{ref=b}{b}[0],\htmlData{ref=b}{b}[1],\ldots,\htmlData{ref=b}{b}[\htmlData{ref=n}{n}-1]$$

and sets $\htmlData{ref=j}{j}=0$.

def _resize(self):
    b = new_array(max(1, 2*self.n))
    for k in range(self.n):
        b[k] = self.a[(self.j+k) % len(self.a)]
    self.a = b
    self.j = 0

Summary

The following theorem summarizes the performance of the ArrayQueue data structure:

Theorem

An ArrayQueue implements the (FIFO) Queue interface. Ignoring the cost of calls to $\mathrm{resize}()$, an ArrayQueue supports the operations $\mathrm{add}(x)$ and $\mathrm{remove}()$ in $O(1)$ time per operation. Furthermore, beginning with an empty ArrayQueue, any sequence of $m$ $\mathrm{add}(i,x)$ and $\mathrm{remove}(i)$ operations results in a total of $O(m)$ time spent during all calls to $\mathrm{resize}()$.

Queue Operations

An SLList can also implement the FIFO queue operations $\mathrm{add}(x)$ and $\mathrm{remove}()$ in constant time. Removals are done from the head of the list, and are identical to the $\mathrm{pop}()$ operation:

def _remove(self):
    return self.pop()
T remove() {
    if (n == 0)    return null;
    T x = head.x;
    head = head.next;
    if (--n == 0) tail = null;
    return x;
}
T remove() {
    if (n == 0)    return null;
    T x = head->x;
    Node *u = head;
    head = head->next;
    delete u;
    if (--n == 0) tail = NULL;
    return x;
}
remove() {
    if (this.n === 0) return null;
    const x = this.head.x;
    this.head = this.head.next;
    if (--this.n === 0) this.tail = null;
    return x;
}

Additions, on the other hand, are done at the tail of the list. In most cases, this is done by setting $\mathit{tail}.\mathit{next}=u$, where $u$ is the newly created node that contains $x$. However, a special case occurs when $n=0$, in which case $\mathit{tail}=\mathit{head}=\mathit{nil}$. In this case, both $\mathit{tail}$ and $\mathit{head}$ are set to $u$.

def _add(self,x):
    u = self.new_node(x)
    if self.n == 0:
        self.head = u
    else:
        self.tail.next = u
    self.tail = u
    self.n += 1
    return True
boolean add(T x) {
    Node u = new Node();
    u.x = x;
    if (n == 0) {
        head = u;
    } else {
        tail.next = u;
    }
    tail = u;
    n++;
    return true;
}
bool add(T x) {
    Node *u = new Node(x);
    if (n == 0) {
        head = u;
    } else {
        tail->next = u;
    }
    tail = u;
    n++;
    return true;
}
add(x) {
    const u = new Node();
    u.x = x;
    if (this.n === 0) {
        this.head = u;
    } else {
        this.tail.next = u;
    }
    this.tail = u;
    this.n++;
    return true;
}

Clearly, both $\mathrm{add}(x)$ and $\mathrm{remove}()$ take constant time.

An SLList nearly implements the full set of Deque operations. The only missing operation is removing from the tail of an SLList. Removing from the tail of an SLList is difficult because it requires updating the value of $\mathit{tail}$ so that it points to the node $w$ that precedes $\mathit{tail}$ in the SLList; this is the node $w$ such that $\mathit{w}.\mathit{next}=\mathit{tail}$. Unfortunately, the only way to get to $w$ is by traversing the SLList starting at $\mathit{head}$ and taking $n-2$ steps.
